# Plan 2F: OTP and Security Frontend Screens — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give customers, business owners and staff every screen the finished OTP backend (Plan 2, `backend/otp/` and the `accounts` sign-in changes) needs before its switches can be turned on: the sign-in code screen, the trusted-device checkbox, a reusable step-up prompt, authenticator-app settings, a security overview with the device list, Super Admin's two OTP numbers, Support's recovery request form and the `otp_sms_spend` notice.

**Architecture:** One new sign-in component (`components/OtpSignIn.jsx`) is shown by `AuthModal` and by `BusinessRegistrationFlow` whenever a login or registration answers a challenge instead of a token; it posts to `/api/otp/sign-in/send/` and `/api/otp/sign-in/verify/` through new `useAuth` methods, and only the final verify stores a session (the same "challenge object, nothing stored" rule the staff 2-step already follows). Step-up is an `apiClient.js` mechanism parallel to `setSudoHandler`: a `403 {code: "step_up_required", action}` from any call asks one registered handler (`components/StepUpPrompt.jsx`, mounted once in `main.jsx`) for a token and retries once with `X-Step-Up-Token`, so wallet withdrawals, payout-destination changes and Money rules reuse it with zero per-screen code. Settings screens are two shared cards (`components/security/`) dropped into the customer `SettingsTab` and the business `ProfilePanel`.

**Tech Stack:** React 19 (Vite), TanStack Query v5, inline `style={{}}` off `C`/`D`, `qrcode` (already used by `components/admin/TwoFactorSetup.jsx`), Vitest + Testing Library + MSW.

**Spec:** `docs/superpowers/specs/2026-10-15-wallet-fees-security-design.md` §9 and its "Before the OTP switches are turned on (Plan 2F)" gate list; requirements row "2F Frontend" in `docs/superpowers/plans/2026-10-16-otp-security.md` (response shapes D7, D8, D12, D13, A12, A13). Owner rulings `wallet-owner-decisions-2026-10-18` (daily wrong-code cap; an opted-in authenticator is honoured even when `OTP_SIGNIN_ENFORCED` is off), built backend-side by Plan 7C Task 6.

## Ordering and dependencies (read first)

- **This plan must ship before ANY OTP switch is turned on** (`OTP_SIGNIN_ENFORCED`, `OTP_STEP_UP_ENFORCED`, `OTP_SIGNUP_VERIFICATION_ENFORCED`). Today `useAuth.login`, `registerCustomer` and `registerBusinessOwner` assume every successful call returns a `token`; with a switch on, a login answers `{otp_required, mfa_token, channels}` or `{two_factor_required, mfa_token}` and a registration answers a challenge with no token, so the current frontend would store `token: undefined` and look signed in. Sign-in switches additionally need `OTP_SMS_PROVIDER=hubtel` working (spec gate), which is outside this plan.
- Plan 7C Task 6 (daily cap; authenticator honoured with the switch off) changes backend behaviour but no endpoint shape. 2F is written to be correct either side of it (Task 6 below handles `available` being false while `enabled` is true). Both must be merged before any switch.
- **Later plans depend on Task 1/2 here:** marketplace Plan 4 (wallet withdrawals), 3F (wallet screens) and the Money rules screen send ordinary `apiPost`/`apiPatch` calls and rely on this step-up mechanism to turn `step_up_required` into a prompt and a retry. They must not build their own code prompt.
- Staff keep password re-entry (`SudoPrompt`, `sudo_required`) for step-up. The one exception is a third-party rider (staff account with Dispatch role), whose withdrawals and payout destinations ask for a code like a customer; the main.jsx-level mount in Task 2 covers the staff shell for that reason.

## Global Constraints

- Frontend commands run from `frontend/` (`cd frontend && npx vitest run <paths>`), never from the repo root. A swarm of `[MSW] intercepted a request without a matching request handler` means a local `frontend/.env` overrides `VITE_API_BASE_URL`; move it aside. MSW is `onUnhandledRequest: 'error'` and `mocks/handlers.js` hardcodes `http://localhost:8000`: every new GET that an existing mounted component now issues (`/api/otp/me/`, `/api/otp/authenticator/`) needs a default handler in `mocks/handlers.js` (Task 8) or unrelated suites fail en masse.
- **Contract tests.** `StaffDashboard.test.jsx` (~60-100 assertions) and `BusinessDashboard.test.jsx` are behavioural contracts: do not edit their existing assertions; additions must not change menu items, tab order or text they assert (no `NAV_ITEMS`/`ROLE_MENUS` entry is added by this plan: "Menu items arrive with their screen", and every screen here lives inside an existing one). `AuthModal.test.jsx` builds a fake `auth` object (`login`, `registerCustomer`, ...) and asserts `auth.login` is called with exactly `('customer', identifier, password)`; keep `login`'s three-argument signature (the device token is read inside `useAuth`, not passed by `AuthModal`) and never call a new `auth.*` method on a path the old tests exercise. `useAuth.test.jsx`, `StaffTwoStepSignIn.test.jsx`, `SudoPrompt.test.jsx`, `apiClient.test.js` and `SecurityPanel.test.jsx` must pass untouched.
- `components/**` must never import `App.jsx`. Anything `App.jsx` owns that these components need is threaded as a prop (`auth` already is). Shared values come from `theme.js` / `components/dashboard/theme.js`.
- Mutations are plain `apiPost`/`apiPatch` in `try/catch` handlers with a local error state, then `refetch()`; no `useMutation`. A component owns its data hook.
- Styling: inline `style={{}}` off the existing palettes (`D` from `components/dashboard/theme.js` in customer/business surfaces, `D` from `components/admin/theme.js` and `panelStyles.js` in staff surfaces); no new colours. Read `DESIGN.md` first: calm, near-neutral forms with white cards on cream and one gold confirm button (as for checkout/KYC); codes use `codeField` (JetBrains Mono); tabular figures on every number (countdowns, device counts); no kente pattern behind the forms; success is kente green and errors kente red.
- **No fabricated data.** There is no way to tell which listed device is the current browser, so the list never marks "this device". There is no code log or text-spend screen, so none is promised. `available: false` is shown as a stated limitation, not hidden. Copy for refusals comes from the server's `detail`; the UI never hard-codes "15 minutes" (after Plan 7C a lock can last until the next day).
- Never put a code, `mfa_token`, `device_token`, step-up token, recovery code or setup secret into a query cache, a URL, the console or `localStorage` (the one exception is the `device_token`, in its own key, Task 3). Typed codes live in component state only; clear them after submit. Hooks that read `/api/otp/*` must not cache secrets (setup/recovery responses are held in component state, not query data).
- Wording: plain, short, no emojis in new copy; the 6-digit code fields use `inputMode="numeric"`, `autoComplete="one-time-code"`, `maxLength={7}` (spaces allowed) and `bareCode()` from `TwoFactorSetup.jsx` before posting. Every status line is `role="status"`, every error `role="alert"`; focus moves to the code field when a stage appears.
- Backend contract being consumed (verified in `backend/otp/*`):
  - Login/registration challenge: `{otp_required: true, mfa_token, channels: [{channel: "sms"|"email", hint}]}`; authenticator: `{two_factor_required: true, mfa_token}`; no contact on file: `409 {code: "no_channel", detail}`. Registration challenge bodies also carry `id`, `full_name` and no `token`.
  - `POST /api/otp/sign-in/send/ {mfa_token, channel}` -> `{channel, hint, expires_in: 300, resend_in: 60}`.
  - `POST /api/otp/sign-in/verify/ {mfa_token, code | recovery_code, trust_device?, device_token?}` -> the normal signed-in body (+ `device_token` when a customer trusted the device), or `{two_factor_required, mfa_token}` after a correct sign-up code when an authenticator is still owed.
  - Error codes on the 400/429/502 bodies (`{detail, code}`): `challenge_expired` (ticket dead: back to the password), `code_expired` (this code is dead: send another), `wrong_code`, `try_later` (429 lock or hourly limit), `resend_cooldown` (429, `retry_after` seconds), `channel_unavailable` (400: offer the other way), `send_failed` (502), `authenticator_unreadable` (400: contact Support).
  - Step-up: `POST /api/otp/step-up/send/ {action, channel}` and `.../verify/ {action, code}` -> `{step_up_token, action, expires_in: 300}`; `409 otp_off` when no code could be owed; refused request shape `403 {detail, code: "step_up_required", action}`; header `X-Step-Up-Token` (CORS allowed). Actions: `payout_destination`, `contact_change`, `authenticator_change`, `password_change`, `withdrawal`.
  - `GET /api/otp/me/` -> `{channels: [{channel, hint, verified}], authenticator, trusted_devices: [{id, label, trusted_since, last_code_at, last_seen_at}], switches: {sign_in, step_up, sign_up}, customer_gap_days}`; `POST /api/otp/devices/<id>/remove/` -> 204; `POST /api/otp/devices/remove-all/` -> `{removed}`.
  - `GET /api/otp/authenticator/` -> `{enabled, enabled_at, recovery_codes_left, available}`; `POST .../setup/` (step-up) -> `{secret, otpauth_uri}`; `POST .../setup/confirm/ {code}` -> `{recovery_codes}`; `POST .../recovery-codes/` (step-up) -> `{recovery_codes}`; `POST .../disable/` (step-up) -> 204. Setup/confirm answer `409 otp_off` while `OTP_SIGNIN_ENFORCED` is off.
  - `GET/PATCH /api/staff-security/policy/` carries `otp: {otp_customer_gap_days, otp_sms_daily_alert}` (limits 1-365 and 1-1,000,000; PATCH needs the password via the existing sudo prompt). `POST /api/otp/recovery/ {account_type: "customer"|"business_owner", account_id, send_to: "sms"|"email", reason}` -> `201 {approval_id, status}`.

## Review Focus

1. **A session stored from a challenge.** Login or registration answering a challenge must store nothing; only a verify (or authenticator) success stores a session. Pinned in Task 3 (`does not store a session for an otp_required answer`, `...for a sign-up challenge`).
2. **Staff and customers on the wrong endpoint.** A non-staff `two_factor_required` posts to `/api/otp/sign-in/verify/`, a staff one stays on `/api/accounts/staff/login/two-factor/`; a staff `otp_required` (staff without an authenticator, switch on) uses the new screen. Pinned in Task 5.
3. **Step-up replay and loops.** One retry only; a second `step_up_required` surfaces; a cancelled prompt surfaces the original 403; a token is sent only when the prompt produced one; it never leaks to another path. Pinned in Task 1.
4. **Trusted-device token handling.** Only customers send/keep it; it survives sign-out (the device stays trusted) but is dropped on "remove all" and when the server stops honouring it. Pinned in Tasks 3-4, 6.
5. **Dead-end states.** `no_channel`, `channel_unavailable`, `send_failed`, `code_expired`, `try_later`, `resend_cooldown` and an authenticator demanded after a sign-up code each have a visible next action. Pinned in Task 4.
6. **Existing suites.** Contract suites and MSW defaults (Global Constraints). Pinned by the full-run in Task 8.

### Task 1: Step-up mechanism in `apiClient.js`

**Files:**
- Modify: `frontend/apiClient.js`
- Modify (add tests only): `frontend/apiClient.test.js`

**Interfaces:**
- Produces `setStepUpHandler(handler) -> unregister` (like `setSudoHandler`). `handler(action: string) -> Promise<string | null>` resolves the step-up token or `null` to cancel. Only the registrant's own `unregister` removes it.
- Behaviour inside `send()`: on a `403` whose JSON `code === 'step_up_required'` and a handler is set, call `handler(body.action)` once; if it returns a token, rebuild the request via `makeInit()` with header `X-Step-Up-Token: <token>` added and retry once; if it returns `null`, return the original 403 response untouched. A second `step_up_required` is returned as is. Sudo and step-up are independent single retries (a request may need both in turn).
- A token whose retried request then fails for any other reason (a 400 validation refusal keeps the token server-side, 5-minute life) is remembered as `{method, path, token, expiresAt}`; the next request with the same method and path within `expiresAt` carries it up front, and it is cleared on any 2xx, on `step_up_required`, on expiry or on sign-out (`setStoredAuth(null)`). `expiresAt` comes from the handler's resolved `{token, expiresIn}`; the handler therefore resolves `{token, expiresIn} | null` (not a bare string).
- Never attach the header to a request whose handler returned nothing; never to a different path.
