# Wallet Rulings 7F-E: Round-3 Rider/Refund Rulings (coupon cap, lock order, AshantiHub-funded promos, re-delivery) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Apply the owner's round-3 rulings (2026-10-19, on the 7F-D report): a coupon refund never makes AshantiHub pay the kept delivery fee out of the subsidy; the pickup/refund lock-order deadlock is removed before the ledger goes live; Marketing can create AshantiHub-funded free-delivery promos that Operations or a Super Admin approve; Support's cancel keeps the pickup evidence; a re-assigned delivery is done by in-house riders and pays only the rider on the current leg; and a re-delivery at the customer's request carries a customer-paid fee.

**Architecture:** (1) `ledger/refunds.py` `left()` learns three figures (what a whole refund can give now, what a partial refund can give, the shortfall AshantiHub covers) and `_post`/`refund_order`/`check` read only those; a public `refunds.refundable(order)` feeds the staff screens. (2) One new module `backend/orders/locks.py` is the only place a `DeliveryAssignment` row lock is taken and it forces the Order row first; `refund_order` and every delivery write path call it. (3) `DeliveryWaiver.funded_by="platform"` (built in 7F-D) gets a creation path: new permission `delivery_promo.fund`, a budget cap, a `marketing.delivery_promo_funding` approval kind decided by Operations or Super Admin (a new `delivery_promo.approve` pool permission), and a form on the staff Free-delivery panel. (4) Re-assignment: `assign()` resets the previous leg's pickup, restricts re-assignments to in-house riders and stamps who picked up; a new `delivery.Redelivery` row plus a `REDELIVERY_FEE` checkout kind and a `REDELIVERY_PAYABLE` account carry the customer-paid second-trip fee. The branch is based on the merged state of 7F-D; the last task rebases onto `origin/righteoushack`.

**Tech Stack:** Django, DRF, Postgres (row locks, `TransactionTestCase` threads), the approvals engine, React (staff Marketing panels), Vitest + MSW.

**Spec:** `docs/superpowers/specs/2026-10-15-wallet-fees-security-design.md` §6, §7, §13 gates (xciii), (xciii-open), (xciv) and new gates after (cxxiii). ## Global Constraints

- **Ruling R1 (binding, round 3): a refund never exceeds what the customer actually paid, net of the coupon, minus the delivery fee kept for the rider.** The customer's real money pays the kept fee first. AshantiHub never pays that fee out of the subsidy by returning the customer money that the fee needed.
- **Reconciliation with 7D ruling 5 / 7F-D (record this wording in the spec).** *Stays:* if the customer paid less than the fee kept (a coupon covered most of it, `N < kept`), a WHOLE refund still pays the rider in full, the customer's credit is 0, and AshantiHub's cost is the gap, taken off the subsidy that would have gone back (`subsidy - shortfall`). This is the coupon doing what it was issued for: it paid part of a fee the customer owed (`Order.delivery_fee > 0`). *Changes:* (a) a partial or shop-scoped refund can no longer hand back customer money the fee needs, so the gap cannot grow; (b) the fee is reserved from the first refund, before a pickup exists; (c) processing money AshantiHub gives back for fault is no longer eaten by the kept fee (it was `max(0, customer + processing - kept)`, it becomes `customer + processing`); (d) the staff "can still be refunded" figure is the real credit. *Not a coupon matter:* a free-delivery promo fee (`Order.delivery_fee == 0`, `WaivedFeeCharge`) is paid by the promo's owner (7F-D Task 2) and is untouched.
- **Canonical lock order (binding, Task 2):** approval/dispute row, then `Order`, then its `OrderFeeSnapshot` rows, then `DeliveryAssignment`, then `PickupStop` rows, then `Rider`, then `Account` rows in one sorted pass (`posting.lock`), then the activity-chain lock. Nothing may take an earlier level while holding a later one. A `DeliveryAssignment` row is locked only through `orders/locks.py`.
- Money is integer pesewas; every journal balances; never put a payout number in a log or event. `OrderRefund.amount_pesewas` from this plan on is the customer's real credit excluding the kept fee (it used to include it); `delivery_kept_pesewas` stays as the record of the fee kept. No back-compat data exists (ledger off in production, 7D/7F-D unpushed), so no data migration.
- AshantiHub-funded promos: money moves only when a rider is owed (7F-D `escrow.settle_delivery`/`charge_waiver`) or at release; this plan adds no ledger posting.
- Frontend: inline `C`/`D` palette, no `useMutation`, panels own their hook, `components/**` never import `App.jsx` (frontend/CLAUDE.md). Run Vitest from `frontend/`. Read `DESIGN.md` before the form layout.
- Test commands: `docker compose run --rm web python manage.py test <labels>` from the repo root.
- **Migrations:** never copy a number from this plan. Every task that adds a migration starts with Step 0: list the app's `migrations/` directory on the branch you are on, run `makemigrations --dry-run`, take the next free number; after any rebase re-run `makemigrations --check` and `showmigrations` for duplicate leaf nodes (Task 9). The branch for this plan is based on the merged state of 7F-D; 7A-7E and 7F-C/7F-D keep merging into `righteoushack` meanwhile.
- **Owner rulings of the round-3 follow-up (binding):** R2 promos approved by Operations or Super Admin (Task 4); R3 re-assignment: first rider unpaid, whole fee to the rider who completes, in-house riders only (Task 6); R4 re-delivery at the customer's request, extra fee paid by the customer, first rider keeps the original fee (Task 7); R5 fee amount as a governed setting (proposed, Task 7).

## Review Focus

- Coupon, no pickup: partial refund capped at `N - F`; whole refund returns `N` (fee included). Coupon, pickup: whole gives `N - F`; partial capped; AshantiHub's cost never above the coupon `D`.
- `N < F` (coupon bigger than the items): customer credit 0, rider paid in full, subsidy credit `D - (F - N)`, journal balances.
- Typing the displayed "can still be refunded" amount produces a WHOLE refund (it equals `Left.customer`), including after a pickup.
- The new race test fails on the 7F-D code (Postgres "deadlock detected") and passes after; no `pg_stat_activity` polling remains in `PickupRaceTests`.
- Nothing in `backend/` outside `orders/locks.py` takes `DeliveryAssignment ... select_for_update` (guard test).
- Support's cancel after a pickup no longer returns the fee and pays the rider; the assignment row survives (Task 3).
- A platform-funded promo waits for Operations or Super Admin, the maker cannot approve it, the old `waivers.approve()` refuses it, a business cannot create one, the cap stops applying the waiver, the funder is copied to the charge at checkout; coupon and campaign kinds stay Super Admin only.
- Re-assignment: the first rider's pickup stops counting; a refund after re-assignment and before the new pickup returns the fee; a re-assignment to a third-party rider is refused; an unaccepted swap is still free.
- Re-delivery: only a failed no-answer trip after arrival qualifies; assignment is gated on the paid fee; refunds before the second pickup return it, after it they keep it; the original fee is paid once, to the first rider (or stays income if in-house); journals balance and reconcile.
- Every migration was numbered on the branch actually built on and the rebase left one leaf node per app (Task 9).

### Task 4: AshantiHub-funded free-delivery promos (backend)

**Where it goes (found by reading):** the business-side screen is `frontend/components/dashboard/panels/DeliveryPromosPanel.jsx` (owner, hook `useOwnerDeliveryPromos`); the staff screen is `frontend/components/admin/panels/marketing/DeliveryPromosPanel.jsx` (tab `mk-delivery-promos`, permission `site_promo.manage`, hook `useStaffDeliveryPromos`). **Ruling R2 (owner, round 3 follow-up; record in the spec):** AshantiHub-funded promos are CREATED by Marketing (new permission `delivery_promo.fund`, held by Marketing and Super Admin) and ALWAYS need approval from Operations OR a Super Admin through the approvals engine (not Super Admin only); the maker never approves their own. There is no threshold shortcut: every AshantiHub-funded promo waits, because it spends AshantiHub's money. A required budget cap bounds the spend. *How Operations is modelled (read in `approvals/registry.py`, `rules.py`, `models.py`, `services.py`):* the engine has no "role" levels; a chain is stages `manager` (the maker's manager), `pool` (anyone holding the kind's `pool_permission`, never the maker) and `super_admin` (anyone holding `approvals.view_all`). So Operations is added by a new permission `delivery_promo.approve`, seeded to the `operations` and `super_admin` roles, set as the kind's `pool_permission`, with `resolve_approver` returning `[(POOL, None), (SUPER_ADMIN, None)]` (no manager stage: Marketing's manager need not be Operations). Operations and Super Admin can both decide at once (Super Admin holds the permission as well); escalation after `response_hours` reaches the same Super Admins. **Left unchanged:** `marketing.coupon` (threshold, Super Admin only), `marketing.campaign`, `marketing.banner`, `marketing.send_policy` (all Super Admin only), and the owner-submitted promo review by `site_promo.manage` staff (`waivers.approve/reject`, business-funded only). ### Task 6: Re-assignment keeps one leg's pickup per rider; only the rider who completes is paid (owner case a)

**Ruling R3 (owner, round 3 follow-up; record in the spec):** (a) When a delivery the first rider picked up but never delivered is re-assigned, the first rider gets NOTHING and the whole delivery fee goes to the rider who completes it. A re-assigned delivery is done by an AshantiHub (in-house) rider only (`Rider.employment == Rider.ASHANTIHUB`).

**How this meets the 7F-D rule "the fee belongs to the rider once any pickup is done" (state exactly):** 7F-D's rule is evaluated on the CURRENT leg: the rider currently on the assignment (`assignment.dispatch_id`) and a pickup THAT rider made. A re-assignment ends the previous leg: the first rider's earlier pickup no longer counts for anyone, so (1) a refund after the re-assignment and before the new rider's pickup finds no pickup and returns the delivery fee to the customer, the first rider unpaid; (2) a refund after the new rider's pickup pays the new rider; (3) a delivery completed by the new rider is paid at release to the new rider (`riders.third_party_rider` already reads the current assignment, and the new rider is in-house, so the fee stays platform delivery income). Nothing is paid to the first rider in any of these. The case where the first rider DID complete the trip and the customer was away is Task 7 and has its own rule (first rider keeps the fee).

**What is wrong today (verified):** `services.assign()` on a failed assignment resets `status`, `accepted_at`, `arrived_*`, `failed_*` but NOT `picked_up_at`, so the first rider's `picked_up_at` survives; `stops.reopen_for_new_rider(failed=True)` clears `PickupStop.collected_at`, but a swap while the assignment is `at_pickup` leaves collected stops collected. `riders.rider_for_settle` then tests the NEW rider's employment against the FIRST rider's pickup time (`employment.third_party_at(rider, pickup_made(order))`). Release (`riders.third_party_rider`) already pays the current `dispatch_id` and ignores a FAILED assignment, so it needs no change except the in-house restriction.
